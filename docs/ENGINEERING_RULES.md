# Patch, verify, then decompose: GAMBIT's rulebook

GAMBIT's first obligation is not architectural. It has to get off **Next.js 14.0.3**. That version is exposed to the critical middleware authorization bypass CVE-2025-29927, which is fixed in 14.2.25 ([GHSA-f82v-jwr5-mffw](https://github.com/advisories/GHSA-f82v-jwr5-mffw)), and to the RSC denial-of-service CVE-2025-55184/CVE-2025-67779, which is fixed in 14.2.35 ([Next.js security update, Dec 2025](https://nextjs.org/blog/security-update-2025-12-11)). The November 2026 security release shipped patches only for **16.4.5 (Active LTS) and 15.5.29 (Maintenance LTS)** ([Nov 2026 Security Release](https://nextjs.org/blog/november-2026-security-release)). The second obligation is trust: the game server currently believes whatever user ID and game result the browser sends. That is OWASP's #1 risk class, Broken Access Control ([OWASP Top 10:2025](https://owasp.org/Top10/2025/0x00_2025-Introduction/)), and it makes ratings meaningless until the server becomes the authority. Several deadlines are also due now or soon. Express 4 has been in maintenance since April 2025 ([Express 5.1 announcement](https://expressjs.com/en/blog/2025-03-31-v5-1-latest-release)). Node 20 reached end of life on 30 April 2026 ([endoflife.date](https://endoflife.date/nodejs)). Supabase's legacy `anon`/`service_role` JWT keys "are being deprecated by the end of 2026" ([Supabase API keys](https://supabase.com/docs/guides/api/api-keys)). The rest of this report turns the research into a binding rulebook with stable IDs (NX, NODE, SEC, SOLID, TEST, GIT). Each rule uses MUST / MUST NOT / SHOULD wording, carries a one-line rationale and a source, and is labeled as either externally sourced or a team convention. A final section explains how to enforce the rules mechanically rather than by goodwill. SOLID is included, deliberately limited by YAGNI and AHA. The aim is to stop new 1,000-line files, not to start a rewrite.

## How the rulebook works: three source classes, one priority ladder

**MUST / MUST NOT** rules block merge. A **SHOULD** rule is the default; departing from it needs a one-line justification in the PR description. Every rule carries a source class:

| Tag | Meaning |
|---|---|
| **[OFFICIAL]** | Taken directly from the vendor's or standard body's own docs: Next.js, Supabase, Socket.io, Express, Redis, GitHub, OWASP, Node.js. |
| **[GUIDANCE]** | Widely cited expert or community guidance: Node.js Best Practices, Martin, Fowler, Dodds, Cockburn, react.dev design advice. Followed by default, but it is a judgment call. |
| **[TEAM]** | A threshold or choice GAMBIT has made where no authoritative number exists, such as file-size limits, patch windows, and PR size. These rules are binding, but the team can retune them in a PR that changes this document. |

Rule IDs are permanent. A retired rule keeps its ID and is marked "withdrawn", so PR comments like "violates NODE-07" keep their meaning.

## Next.js rules: upgrade to an LTS line, then treat every server entry point as public

The core Next.js lesson of 2025–26 is that **authorization checks must live next to the data, not in middleware**. CVE-2025-29927 showed that a check performed only in middleware could be bypassed by sending one header ([GHSA](https://github.com/advisories/GHSA-f82v-jwr5-mffw)). Next.js's own guide now says middleware/proxy is for "optimistic checks" only and "should not be your only line of defense" ([Authentication guide](https://nextjs.org/docs/app/guides/authentication)). Caching has also changed direction three times. Next 14 cached GET Route Handlers by default ([Next.js 15 blog](https://nextjs.org/blog/next-15)). Next 15 stopped caching `fetch`, GET handlers and client navigations. Next 16's Cache Components made caching "entirely opt-in" via `"use cache"` ([Next.js 16 blog](https://nextjs.org/blog/next-16)). For a real-time chess site, cached per-user data is a correctness and privacy bug. The November 2026 advisories describe cross-user cache disclosure through `use cache` ([Nov 2026 release](https://nextjs.org/blog/november-2026-security-release)).

**Upgrade path:** 14.0.3 → **14.2.35** immediately (stopgap) → **15.5.x** (run the `next-async-request-api` codemod; React 19; Node ≥18.18) → **16.4.x** (rename `middleware.ts`→`proxy.ts`, migrate `next lint` to the ESLint CLI, make `revalidateTag` calls two-argument; Node ≥20.9, TS ≥5.1) ([Next 15](https://nextjs.org/blog/next-15); [Next 16](https://nextjs.org/blog/next-16)). Rename to `proxy.ts` only once you are on Next 16. On 15 and earlier "a `proxy.ts` file is never called, so sessions never refresh" ([Supabase SSR guide](https://supabase.com/docs/guides/auth/server-side/nextjs)). The research did not find an official 14.x end-of-life page; "14.x is unsupported" is inferred from its absence in the 2026 security releases.

## Node.js rules: the server owns the game, and Redis owns the state

The game server's design flaw is not that `server.js` is 800 lines long. The flaw is that **the client is the authority on identity and outcome**. Socket.io already provides the right hook: `io.use` middleware runs "once per connection" and reads credentials from `socket.handshake.auth` ([Socket.io middlewares](https://socket.io/docs/v4/middlewares/)). Supabase documents how to verify its JWTs against the project JWKS, or with `getClaims()` ([Supabase JWTs](https://supabase.com/docs/guides/auth/jwts)). Once identity is verified, every move must be checked against server-held state. That state cannot live in process memory: "you cannot maintain state in the application code" across instances ([Express performance](https://expressjs.com/en/advanced/best-practice-performance.html)), and a Railway redeploy sends SIGTERM and then SIGKILL to the old instance ([Railway teardown](https://docs.railway.com/deployments/deployment-teardown)). Redis supplies the atomicity: a Lua script is "usually… both simpler and faster" than MULTI/WATCH ([Redis transactions](https://redis.io/docs/latest/develop/using-commands/transactions/)).

Two platform facts set the timeline. Express 4 entered MAINTENANCE on 1 April 2025, with an EOL target of "no sooner than 2026-10-01". The project says it "may extend" support for v4, and its dates are "goals not commitments" ([Express 5.1 blog](https://expressjs.com/en/blog/2025-03-31-v5-1-latest-release)). Whether v4 has actually reached EOL could not be confirmed, so treat it as end-of-life-imminent. Express 5 also forwards async errors to the error handler natively ([Express perf](https://expressjs.com/en/advanced/best-practice-performance.html)). For Node, line 26 is Active LTS (security support to April 2029), 24 is in maintenance (to April 2028), 22 gets security fixes until April 2027, and 20 is EOL ([endoflife.date](https://endoflife.date/nodejs)). From 27.x, Node moves to one major release a year, and every release becomes LTS ([Node.js release schedule](https://nodejs.org/blog/announcements/evolving-the-nodejs-release-schedule)).

## Security rules: the database, not the client, defends the rating column

Every app-level fix above can be bypassed if Postgres itself allows the write, so the security rules make the database the last line of defense. Supabase's documentation identifies GAMBIT's rating bug exactly: RLS gives the row owner "full access to update the row, including all of the columns" ([Supabase CLS](https://supabase.com/docs/guides/database/postgres/column-level-security)). The robust fix is to remove client write paths to ratings altogether. Results and ratings go through a `security definer` function with `search_path = ''` and EXECUTE granted only to `service_role`, called by the game server ([Supabase functions](https://supabase.com/docs/guides/database/functions)). Supabase calls column-level privileges "an advanced feature" it does "not recommend… for most users" ([Supabase CLS](https://supabase.com/docs/guides/database/postgres/column-level-security)). GAMBIT uses them anyway as a second layer, because ratings are the one column whose integrity defines the product.

## SOLID rules: decompose by who asks for changes, and stop when it stops paying

SOLID is often misread as "make everything small". Martin's own definition of SRP is about people: "a module should be responsible to one, and only one, actor" ([Clean Architecture ch.7](https://www.oreilly.com/library/view/clean-architecture-a/9780134494272/ch7.xhtml)). It means "gather together the things that change for the same reasons" ([Martin 2014](https://blog.cleancoder.com/uncle-bob/2014/05/08/SingleReponsibilityPrinciple.html)). For GAMBIT, the change-drivers are clear. Chess rules, UX, infrastructure (Supabase/Redis/transport), rating policy and social features each change for different reasons. A 1,000-line game page that mixes socket wiring, chess rules, fetching and JSX answers to all of them, so every change to any one of them collides with the others. The other four principles also translate cleanly into TypeScript without classes. OCP means adding a time control without editing the game loop ([Martin 2020](https://blog.cleancoder.com/uncle-bob/2020/10/18/Solid-Relevance.html)). LSP means every implementation of an interface behaves the same way: same not-found and error semantics ([Liskov & Wing 1994](https://www.cs.columbia.edu/~wing/publications/LiskovWing94.pdf)). ISP means narrow props and parameters ([Lebedev](https://medium.com/dailyjs/applying-solid-principles-in-react-14905d9c5377)). DIP means dependencies point toward policy and away from Supabase and sockets. Dependency Inversion is not the same thing as a DI container ([Stemmler](https://khalilstemmler.com/articles/tutorials/dependency-injection-inversion-explained/)).

The limits matter just as much. Fowler's YAGNI forbids building "presumptive features", but "Yagni is not a justification for neglecting the health of your code base" ([Fowler](https://martinfowler.com/bliki/Yagni.html)). AHA, following Sandi Metz, says to "prefer duplication over the wrong abstraction" ([Dodds, AHA](https://kentcdodds.com/blog/aha-programming)). React's docs agree that "some duplication is fine" and warn against `useMount`-style wrapper hooks ([react.dev](https://react.dev/learn/reusing-logic-with-custom-hooks)). Dan North's CUPID critique calls one-reason-to-change "often a premature segregation" ([North](https://dannorth.net/blog/cupid-for-joyful-coding/)). His example is splitting rendering from logic that always changes together. That critique is fair, so the rulebook ties every abstraction to a concrete justification.

## Conclusion

The research shows that GAMBIT's highest-leverage rules are not the SOLID rules. They are the **trust-boundary rules**: verify identity at the handshake, adjudicate games on the server, write ratings only through a locked-down database function, and never let middleware or the client be the last check. The same lesson appears independently in every source. Next.js retreated from middleware-only auth after CVE-2025-29927. Supabase says plainly that cookies can be forged and that RLS alone doesn't protect columns. Socket.io warns that CORS doesn't cover WebSockets. A chess platform whose ratings can be self-assigned has no product to protect, so these rules outrank everything else in the book.

The second insight is that the version treadmill is now a governance problem, not an occasional chore. Next.js runs scheduled security releases that patch only two lines. Node moves to one LTS a year from 27.x. Express 4's end of life is a moving target, and Supabase's key formats change by year-end. A team that pins versions in rules (NX-01, NODE-01, SEC-05) and bounds patch windows (NX-02) will spend hours per quarter on upgrades instead of weeks per incident. SOLID then earns its place mainly through dependency direction (SOLID-06/07), which is what makes the authoritative server testable. Its size proxies are deliberately labeled team conventions and enforced as a ratchet, so the rulebook pushes new code toward better structure without forcing a rewrite. Several points remain unverified and should be checked before relying on them: Railway's support for sticky sessions, Express 4's actual EOL status, the exact `supabase db advisors` CI flags, and the official 14.x end-of-life date.
