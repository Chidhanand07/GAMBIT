## Behaviour changes users will notice

- **A deploy no longer cuts games off silently.** Clients are told the server is going away and reconnect; with two or more replicas they land on another one and the game continues. With one replica a deploy of over ~20 s can still end games by abandonment.
- **Networks that block WebSockets cannot play** (HTTP long-polling is gone; it needs sticky sessions). All supported browsers have WebSocket.
- `/api/matchmaking/status` may be up to ~1 s stale on a replica that is not running the pairing pass.
- Error responses of the game server's HTTP API are JSON everywhere (404, 400, 413 were HTML).
- Nothing visual changes. The only frontend change is `transports: ['websocket']` in `lib/socket/connection.ts`.

## Deploy

1. **Vercel (web app) first:** the WebSocket-only client also works with the old server.
2. **Railway (game server):** optional `LOG_LEVEL` (default `info`); `SOCKET_ADAPTER` unset or `redis` (the default; `none` only for a single local instance). Keep **one replica** for this deploy.
3. Watch the logs: JSON lines with `service: "gambit-server"`. `GET /readyz` → 200 with both checks ok.
4. Switch Railway's healthcheck path from `/api/health` to `/readyz` (optional, recommended).
5. **Scaling** (separate step, after a day on one replica): follow DEPLOY.md §4b-2 — Redis with Lua and Streams (a Railway Redis add-on is cheaper than per-command Upstash with blocking `XREAD`), then 2 replicas, then the two-replica manual test below.
6. **GitHub:** add the repository secrets `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD`, `SUPABASE_PROJECT_REF` for the drift check; keep CodeQL on advanced setup (the workflow), not default setup.

**Rollback:** scale back to 1 replica first, then redeploy the previous server build. Game state written by this version is the same JSON as before (the compare-and-set writes the same keys); the `{mm}:*` queue keys and `clocktick:*` locks are ignored by the old code and expire on their own (players in the queue at that moment must search again). The WebSocket-only web app works with the old server; roll it back only if needed.

## Found by the new tests

- **Every disconnect would have thrown with the Redis adapter.** `socket.data` held the pino child logger; the Streams adapter msgpack-encodes `socket.data` for connection-state recovery and cannot encode a function. Fixed (the logger is not stored on the socket) and pinned.
- **Recovery sessions could be lost at shutdown.** The adapter's Redis connection was closed with `disconnect()`, dropping the session writes `io.close()` had just queued. It now uses `quit()`.

## Manual tests

1. Deploy with one replica. `GET /livez` → 200; `GET /readyz` → 200; stop Redis briefly → `/readyz` 503 naming `redis`.
2. Start a game in two browsers, then redeploy the server: both see a reconnect, the board re-syncs, the game continues if the deploy is fast.
3. Two replicas: two browsers, two accounts, until the logs show the two sockets on different replicas (`hostname` in the JSON lines, added in this PR). Search for a game (they must be paired), play to mate: moves, clocks, chat, resign, rematch reach both sides; exactly one rating change.
4. Two replicas: open the same game in a second tab on the other replica, close the first tab → no "opponent disconnected" countdown for the opponent.
5. Two replicas: restart one replica mid-game → its player reconnects to the other, clocks did not run twice.
