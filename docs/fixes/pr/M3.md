## Behaviour changes users will notice

- Previews on `*.vercel.app` other than this project's cannot reach the game server any more (they could, with credentials). Set `CORS_PREVIEW_ORIGIN_REGEX` to allow your own.
- Bursts are refused: e.g. more than 5 chat lines in 10 s, more than 10 login attempts for one e-mail in 15 min, more than 5 sign-ups per hour from one IP. The client gets 429 / `rate_limited` with a retry time.
- When the engine is saturated, analysis and the computer opponent answer quickly with "Engine busy" (the computer opponent currently shows a generic engine error).
- Game reviews of games without moves are no longer produced; a side that made no move shows no accuracy instead of 100.
- Mates and moves such as `Nbd7` are classified correctly in reviews (but see "Known problem" below).
- An off-site `?next=` / `?redirect=` after sign-in goes to `/lobby`.

## Deploy

1. **Migration first** (staging, then production): `supabase/migrations/20261113100000_rating_atomic.sql`. It is additive (a nullable column, a backfill of `rated_at` for existing completed games, a function); the currently deployed server keeps working. Do not re-run its backfill after the new server is live. A server deployed *before* the migration rates nothing (logged per game).
2. **Railway (game server):** set `CORS_ORIGINS` (required in production; the production URL and custom domains, comma-separated). Optional `CORS_PREVIEW_ORIGIN_REGEX`.
3. **Vercel:** optional but recommended `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` (read-write REST token, server-only). Without them the web app's rate limits are off (logged).
4. **Render (engine):** the service must use the Docker runtime from the root `render.yaml` (an existing native-Python service may need recreating). Optional `ENGINE_MAX_QUEUE`, `ENGINE_QUEUE_TIMEOUT_SECONDS`, `MAVERICK_MODEL_URL` + `MAVERICK_MODEL_SHA256`.
5. Deploy engine, server, web. Then smoke-test one rated game and check both ratings changed (see "Not verified").

**Rollback:** redeploy the previous builds. Leave the migration in place (the old server ignores `rated_at` and the function). Remove `CORS_ORIGINS` only together with the old server.

## Known problem found, not fixed (outside the listed items)

The stockfish package reports `get_evaluation()` from White's side, but the review code assumes the side to move and always negates: with the real binary **every White move in a game review is mis-scored** (1.e4 shows as an "Inaccuracy"). The test fake has the same wrong assumption. Same issue in `computer_engine.py` when MAVERICK plays Black. Recommended as the first fix of the next phase (F-048).
